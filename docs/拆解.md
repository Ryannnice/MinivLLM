# 拆解：按《scaling-book》章节看 vLLM / vLLM-Ascend 的技术体现、工程方案与源码分析

> 版本与证据范围：本文当前基线基于 `scaling-book` 在线目录（2026-05-01 可访问版本）与两套源码快照：`vllm` 固定到 `92a7c121b62a1484b68c0a27d1ecefd1a84f78fc`，`vllm-ascend` 固定到 `d1f66849c9ea1459ca6a4c6c213ac3fec2ec1c9c`。本文按《scaling-book》的章节顺序组织，并保留其在线目录里“GPU 章位于结论和进一步阅读之后”的原始排布；但不强求每章都与 vLLM 一一同构。对于关联较弱的章节，会显式写明“关联较弱”而不是强行拔高。

> 写作约定：每章都按五件事展开。`核心问题` 说明该章在大模型系统中的关注点；`vLLM 的技术体现` 说明 upstream vLLM 如何把这个问题工程化；`工程技术方案` 解释它在运行时里如何落地；`源码分析` 说明最值得顺着追的对象、字段、函数与调用链；`vLLM-Ascend 补充` 只在确有平台实现差异时展开，弱相关章节会明确写“暂无明显 Ascend 特化”。

## 第 0 部分. 简介

### 核心问题
《scaling-book》的出发点是把“大模型为什么能扩展”从数学、硬件、并行、训练、推理、服务几个层面串成一个系统问题。对 vLLM 而言，这个系统问题被进一步收束成在线推理系统的三个核心矛盾：不规则请求、超大的 KV cache，以及高频 decode 下的固定开销。

### vLLM 的技术体现
vLLM 不是“某个 attention kernel 的集合”，而是一个把 `engine -> scheduler -> KV cache -> worker -> backend` 串起来的推理操作系统。`v1/engine/core.py` 负责搭起 EngineCore 与 executor、scheduler、KV cache 的总装线；`v1/core/sched/scheduler.py` 决定每一步算谁、算多少；`v1/core/kv_cache_manager.py` 把 block 化的 KV 当成可调度资源；`v1/worker/gpu/model_runner.py` 与 `v1/attention/` 负责把这些抽象真正压到设备执行路径。

### 工程技术方案
vLLM 的第一性原理不是“把整批请求推进一个阶段”，而是把每个请求建模成“还欠多少 token 没算”，再让 scheduler、KV 管理器与 backend 围绕这个 debt 联动。这样，prefill、decode、prefix cache、spec decode、KV transfer、disaggregated prefill 都能落到同一个核心执行框架上。

### 源码分析
真正的主链要从三个文件一起读：

- `vllm/v1/engine/core.py`：看 `add_request()`、`step()` 如何把上层请求接到 scheduler。
- `vllm/v1/core/sched/scheduler.py`：看 `schedule()` 如何围绕 `num_computed_tokens` 和 `num_tokens_with_spec` 推进请求。
- `vllm/v1/core/kv_cache_manager.py`：看 prefix hit、admission、slot 分配如何进入调度主路径。

如果只读模型文件或单个 kernel 文件，会误判 vLLM 的重心在算子而不在 runtime。

### vLLM-Ascend 补充
Ascend 没有推翻这套总框架，而是把同样的 `engine -> scheduler -> KV cache -> worker -> backend` 运行时重新接到了 NPU 世界：平台入口由 `vllm_ascend/platform.py` 接管，attention runtime 由 `vllm_ascend/attention/attention_v1.py` 与 `vllm_ascend/worker/model_runner_v1.py` 重建，图执行则由 `vllm_ascend/compilation/acl_graph.py` 负责。也就是说，Ascend 的主要增量是把 vLLM 的稳定系统边界换成 NPU 可执行实现。

## 第 1 部分. Roofline 模型简介

### 核心问题
Roofline 关心的是“某段计算到底受算力限制还是受带宽限制”。这对 LLM serving 尤其重要，因为 prefill 和 decode 的瓶颈形态并不相同：长 prompt prefill 更容易逼近计算密度，而单步 decode 往往更接近 memory-bound 与 runtime-bound。

### vLLM 的技术体现
vLLM 的很多优化本质上都在做 roofline 对齐。prefill 侧通过 FlashAttention、chunked prefill、context parallel 等手段提高大块计算效率；decode 侧则通过 paged attention、block table、CUDAGraph、prefix caching、spec decode 来减少显存访存与 host-side 固定成本。`scheduler.py` 中的 `token_budget`、`encoder_compute_budget`，以及 `attention/backends/` 与 `attention/ops/` 中对 prefill/decode 的区分，正是在系统层承认两类路径的瓶颈不同。

### 工程技术方案
vLLM 没有显式把 roofline 画成论文里的图，但它做了等价的工程分层：

1. 对计算密集型路径，尽量把大 token 块塞进高效 attention backend 与 graph capture。
2. 对带宽/调度敏感路径，尽量减少每步重排、KV 拷贝和无效 prefix 重算。
3. 对无法单靠 kernel 优化解决的瓶颈，则把问题上移到 scheduler、cache system 和 graph runtime。

### 源码分析
这一章最值得追的不是单个 FLOPs 公式，而是“谁在承认瓶颈差异”：

- `vllm/v1/attention/backends/flash_attn.py`：prefill 路径如何把大块计算压到高效 backend。
- `vllm/v1/attention/ops/paged_attn.py`：decode 如何围绕 block table 读取 KV。
- `vllm/compilation/cuda_graph.py`：为什么 decode 高频小步要优先削减 launch/runtime 常数项。
- `vllm/v1/core/sched/scheduler.py`：为什么 token budget 和 encoder budget 会出现在同一个调度器里。

### vLLM-Ascend 补充
本章没有单独的 roofline 分析器级增量，Ascend 的差异主要体现为执行路径上的常数项重写：`ACLGraph` 压低小步 decode 固定开销，`attention_v1.py` 处理 NPU workspace 与 paged attention/FIA 分流，`scheduler_dynamic_batch.py` 与 `scheduler_profiling_chunk.py` 则把 token budget 调优做成运行时策略。换句话说，Ascend 在 roofline 章节没有“额外理论”，而是把 roofline 判断落实为后续 runtime 优化。

## 第 2 部分. 关于 TPU 的一切

### 核心问题
这章在书里讨论的是“如何从硬件约束反推软件结构”。对 vLLM 来说，真正对应的不是 TPU 本身，而是“如何把推理引擎做成多后端平台抽象，而不是把 CUDA 假设写死到所有层”。

### vLLM 的技术体现
upstream vLLM 已经在 `platforms/`、`config/device.py`、`config/parallel.py`、`v1/worker/` 里把平台差异抬成一等公民。也就是说，vLLM 的代码结构早就不只是“CUDA 版 LLM 推理器”，而是在平台层声明 `cuda/cpu/tpu/xpu/...`，在 worker 输入批次、attention backend、executor 与 distributed communicator 层做差异分发。

### 工程技术方案
vLLM 没有把 TPU 的语义写进主调度器，而是把平台依赖尽量封在：

1. `platforms/*.py` 的设备能力与 runtime 选择；
2. `worker/*` 的设备输入批次与模型运行器；
3. `distributed/*` 的通信后端；
4. `compilation/*` 的图捕获与编译栈。

这种切法直接为后续 vLLM-Ascend 这类插件式扩展提供了接口边界。

### 源码分析
这一章最值得看的不是 TPU 文件本身有多长，而是“平台抽象在什么层被建立”：

- `vllm/platforms/interface.py`：平台抽象入口。
- `vllm/platforms/tpu.py`：upstream 已经接受“TPU 是独立平台”这一事实。
- `vllm/config/device.py`：设备选择进入正式配置面。
- `vllm/v1/worker/tpu_input_batch.py`：输入批次也是设备相关对象，而不是统一无差别结构。

### vLLM-Ascend 补充
这是 Ascend 最强的一章之一。`vllm_ascend/platform.py` 中的 `NPUPlatform` 明确重写了 `device_name / dispatch_key / compile backend / pass manager / quantization registry`，把上游默认的 CUDA 假设切到 `torch.npu` 与 `PrivateUse1` 派发。配套地，`vllm_ascend/ascend_config.py` 聚合了 PCP/DCP、flashcomm2、sparse C8、dynamic batch、CPU binding 等平台附加配置，`vllm_ascend/distributed/device_communicators/pyhccl.py` 与 `npu_communicator.py` 则把通信语义改写到 HCCL/NPU 通道上。书里谈 TPU，是在强调“别把设备差异藏成一堆 if-else”；Ascend 插件正是把这个思想做成了一个完整的 OOT 平台层。

## 第 3 部分. 分片矩阵以及如何乘以它们

### 核心问题
分片矩阵乘法对应的是大模型并行化的物理现实：权重放不下、单卡吞吐不够、通信与计算必须共同设计。对推理引擎来说，这件事最终体现在 tensor parallel、expert parallel、all-reduce/all-gather/all-to-all、sharded weight loading 等机制里。

### vLLM 的技术体现
vLLM 在 `model_executor/layers/linear.py` 中把张量并行线性层做成统一抽象，覆盖 column parallel、row parallel、merged column、QKV column 等模式；在 `distributed/parallel_state.py` 和 `distributed/communication_op.py` 中维护模型并行进程组；在 `device_communicators/` 中为不同设备后端实现 all-reduce 与 all-to-all 通路。

### 工程技术方案
vLLM 的工程取向不是自己发明新的分片理论，而是把分片的后果压到模块边界里：

1. 层定义负责权重形状与 shard loader；
2. distributed 状态负责进程组与 collective；
3. model runner 负责在推理图里组织实际执行；
4. expert parallel 则继续通过 `distributed/eplb/` 等模块做负载均衡和拓扑协调。

### 源码分析
源码上最有信号的是三条链：

- `vllm/model_executor/layers/linear.py`：`ColumnParallelLinear`、`RowParallelLinear`、`QKVParallelLinear` 这些类决定“权重如何切”。
- `vllm/distributed/parallel_state.py`：决定“切开的东西在哪些 rank 上通信、谁和谁是一组”。
- `vllm/model_executor/models/llama.py` 等模型文件：决定“这些分片线性层如何真正装入模型块”。

也就是说，书里的“分片矩阵怎么乘”，在 vLLM 里被拆成“层抽象 + 进程组 + 模型接线”三层。

### vLLM-Ascend 补充
Ascend 在推理侧真的做了“分片矩阵 + 通信 + 图融合”的专门重写。`vllm_ascend/distributed/parallel_state.py` 新增了更细粒度的 TP/shard-weight/flashcomm2 并行组；`vllm_ascend/ops/layer_shard_linear.py` 与 `flashcomm2_oshard_manager.py` 把 layer-shard 与 attention `o_proj` 的 O-shard 单独管理；`vllm_ascend/compilation/passes/sequence_parallelism.py`、`sequence_parallelism_moe.py`、`allreduce_rmsnorm_fusion_pass.py` 则说明 Ascend 不满足于复用上游 collective，而是在 graph pass 层直接把 all-reduce/all-gather 与 norm/matmul 融到 NPU 更偏好的执行形态。

## 第 4 部分. 你需要知道的所有 Transformer 数学

### 核心问题
这章在书里谈的是 Transformer 本体：QKV、RoPE、注意力、MLP、归一化、多头/多查询/MLA 等。vLLM 的对应点不是“再讲一遍数学”，而是解释它如何把这些算子包装成适合在线推理的后端与缓存接口。

### vLLM 的技术体现
vLLM 在 `model_executor/models/` 里维护模型定义，在 `model_executor/layers/` 与 `v1/attention/` 里维护推理时真正需要的算子拼装与 backend 选择。注意力不是一个固定实现，而是 `flash_attn / flashinfer / triton / paged_attn / MLA / mamba_attn` 这类后端的集合；RoPE、QK norm、KV cache layout、prefix prefill 也都不是孤立函数，而是围绕模型结构与缓存布局共同设计。

### 工程技术方案
对 Transformer 数学的“工程化翻译”主要体现在三点：

1. 统一的 attention backend 选择与 metadata 构造；
2. 模型结构与 KV cache 接口解耦，使不同架构共享调度和缓存系统；
3. 将 RoPE、QKV、quantization、MLA 等变体前移到 backend / pass / model_runner 层处理，而不是污染顶层调度器。

### 源码分析
本章要重点看“数学对象如何被 runtime 接口化”：

- `vllm/v1/attention/backend.py`：attention backend 抽象把“注意力数学”变成“可派发的执行契约”。
- `vllm/v1/attention/selector.py`：决定不同模型/shape/平台走哪个后端。
- `vllm/model_executor/models/qwen3.py`、`llama.py`：模型层如何把 QKV、RoPE、MLP 接到统一层体系。
- `vllm/v1/kv_cache_interface.py`：KV cache 不是模型内部私有状态，而是统一接口。

### vLLM-Ascend 补充
Transformer 数学本身没有因为 Ascend 而改变，变化发生在执行约束而不是定义层。`attention_v1.py / mla_v1.py / sfa_v1.py` 把 KV layout、workspace、paged attention/FIA 路径、graph metadata 都做成了 NPU runtime 契约，因此本章与 Ascend 的对应主要落在“数学对象如何被执行”，而不是“数学本身如何改写”。

## 第 5 部分. 如何为训练并行化 Transformer

### 核心问题
这章原本讲训练时的数据并行、张量并行、流水并行、激活重算与通信调度。对 vLLM 来说，直接对应关系并不强，因为它不是训练框架；但“如何把 Transformer 拆开并在多设备上组织执行”依然会以推理版形式出现。

### vLLM 的技术体现
vLLM 明确把自己定位为推理系统，所以它不实现 optimizer、backward、梯度同步这条链；但训练并行里最核心的分解思想，仍然保留在推理运行时中：张量并行与 expert parallel 继续存在，上下文并行在 prefill/decode 两侧仍然是现实需求，某些 compile pass 依然会重写执行边界。

### 工程技术方案
这一章对 vLLM 的价值，不是“复刻训练系统”，而是界定清楚推理系统接了哪些并行化遗产、又明确舍弃了哪些环节。也正因为这个边界清晰，vLLM 才能把大部分复杂度集中到调度、KV cache 与执行图，而不是被训练状态管理拖住。

### 源码分析
这一章的源码要带着“边界感”读：

- `vllm/config/parallel.py`：推理侧有哪些并行 knob，说明它借用了哪些训练并行词汇。
- `vllm/distributed/parallel_state.py`：推理世界怎样维护这些并行组。
- `vllm/compilation/passes/fusion/sequence_parallelism.py`：推理图也会吸收 sequence parallel 思想，但服务对象是 inference graph。

结论不是“vLLM 也在做训练并行”，而是“它只继承训练并行里对推理有价值的那部分原语”。

### vLLM-Ascend 补充
这一章与 Ascend 仍然是弱映射关系。Ascend 虽然有 `sequence_parallelism`、TP/EP group 与 context parallel attention，但它们服务的是推理图、通信和 backend 优化，而不是训练态的 optimizer、backward 或 checkpoint pipeline；因此它复用的是训练并行的原语名称，而不是训练框架本身。

## 第 6 部分. 在 TPU 上训练 LLaMA 3

### 核心问题
这一章是“把前面所有通用原则落到一个具体硬件和一个具体模型”的应用章节。对 vLLM 来说，最接近的对应不是训练 LLaMA，而是“把一个具体模型家族接到统一推理运行时，并根据硬件/执行器差异选定实现路径”。

### vLLM 的技术体现
vLLM 通过 `config/model.py`、`model_executor/models/`、`engine/core.py` 和 `worker/*model_runner*.py` 形成模型接入链：配置层描述模型能力，模型定义层给出层级拼装，model runner 决定真实执行，scheduler/KV cache 再为它提供统一服务。

### 工程技术方案
upstream vLLM 的应用化路径更偏“模型接线 + runtime 适配”：

1. 通过模型注册和 config，把不同架构装到统一执行框架；
2. 通过 worker/model_runner 适配设备与 backend；
3. 通过 executor 决定单进程、多进程、Ray 等运行形态。

### 源码分析
这一章可以把“应用化能力”顺着三层读：

- `vllm/config/model.py`：模型配置统一入口。
- `vllm/model_executor/models/registry.py`：模型是如何被注册和发现的。
- `vllm/v1/worker/gpu/model_runner.py`：最终由谁把这些模型配置变成真实执行。

它与训练 recipe 的差异在于：这里缺少 optimizer、checkpoint save、训练数据管线，但非常强调“模型如何被接到 serving runtime 里”。

### vLLM-Ascend 补充
这一章没有直接对应物。vLLM-Ascend 的 applied work 是“把推理与服务跑在 Ascend 上”，不是“在 Ascend/TPU 上训练 LLaMA”；缺失的正是 optimizer、训练 driver、data pipeline 与 checkpoint orchestration 这类训练栈，因此这里的映射边界停在模型接入与运行时装配。

## 第 7 部分. 关于 Transformer 推理的一切

### 核心问题
这是与 vLLM 最直接对齐的一章。书里会讨论 KV cache、prefill/decode、speculative decoding、吞吐/延迟平衡与内存系统；这些正是 vLLM 的主战场。

### vLLM 的技术体现
`scheduler.py` 的核心注释已经把设计讲清楚了：调度器不再区分“prefill phase”与“decode phase”，而是让每个请求的 `num_computed_tokens` 追上 `num_tokens_with_spec`。围绕这个主抽象，`kv_cache_manager.py` 负责 prefix hit 与 slot 分配，`kv_cache_coordinator.py` 负责更底层的 block/prefix/window 组织，`spec_decode/` 负责 speculative proposal/verification 路径，`worker/gpu/block_table.py` 与 `attention/ops/paged_attn.py` 则把 paged KV 真正转成可执行数据结构。

### 工程技术方案
这一章里最关键的不是单点算子，而是四层协同：

1. `continuous batching`：每步重调度，让新旧请求共存；
2. `PagedAttention / KV blocks`：把 KV 变成 block 池而不是大块连续数组；
3. `prefix caching`：把共享 prompt 的重复工作降到 block 命中问题；
4. `spec decode / jump decode`：把未来 token 也并入调度 debt，而不是单独开一套执行框架。

### 源码分析
这一章必须顺着一条源码因果链去看：

1. `vllm/v1/core/sched/scheduler.py`：`num_new_tokens` 的计算、`allocate_slots()` 的调用、preemption 的触发，说明调度器真正在调什么。
2. `vllm/v1/core/kv_cache_manager.py`：`get_computed_blocks()` 会故意让全 prompt hit 也重算最后一个 token，说明 prefix cache 的目标不是“完全不算”，而是“保留 logits 所需最小重算”。
3. `vllm/v1/core/block_pool.py`：`free_block_queue` 和 `cached_block_hash_to_block` 说明 block pool 同时承担 allocator 和 prefix-cache index 的职责。
4. `vllm/v1/worker/gpu/model_runner.py`：`InputBatch`、`seq_lens_cpu_upper_bound`、`prepare_attn()` 说明调度结果如何变成设备执行输入。

### vLLM-Ascend 补充
Ascend 在这一章的增量最集中。`vllm_ascend/attention/attention_v1.py` 不只是换 kernel，而是重写了 `get_kv_cache_shape / swap_blocks / copy_blocks / metadata builder / update_graph_params` 这整条 attention runtime，并把 paged attention 与 FIA 的分支逻辑显式化；其中 metadata builder 还直接编码了 graph capture 支持与 decode threshold 约束。`vllm_ascend/attention/mla_v1.py` 进一步把 MLA 路径、量化与 KV 组织绑到 NPU 限制上；`vllm_ascend/worker/model_runner_v1.py` 和 `worker/v2/model_runner.py` 则把 ACLGraph、`seq_lens_cpu`、spec decode 等逻辑并进主 runner。再往下，`vllm_ascend/kv_offload/cpu_npu.py` 与 `spec_decode/dflash_proposer.py` 说明 Ascend 连 KV offload 与 speculative decode 的细节都没停留在“兼容即可”的层面。

## 第 8 部分. 在 TPU 上服务 LLaMA 3

### 核心问题
这一章讲的是“从推理算法走到服务系统”：请求生命周期、并发、流式输出、部署拓扑、分离式 prefill/decode、调度与资源隔离。对 vLLM 来说，这正是 `LLMEngine + EngineCore + executor + connector` 这条链。

### vLLM 的技术体现
用户侧请求先进入 `v1/engine/llm_engine.py` 和 `input_processor.py`，再由 `EngineCoreClient` 发送到 `EngineCore`；`EngineCore` 初始化 scheduler 与 executor，并通过 `step()` 主循环驱动 worker。多进程与多机部署则由 `v1/executor/`、`distributed/kv_transfer/`、`distributed/ec_transfer/` 提供分离式能力。

### 工程技术方案
这一章对应的系统设计包括：

1. 前台 API/请求对象与后台 EngineCore 解耦；
2. 单机、多进程、Ray 三种执行器路径；
3. KV connector / EC connector 支撑 disaggregated prefill、远程 KV 迁移、offload；
4. output processor / detokenizer / async_llm 把底层 token 流变成用户可消费输出。

### 源码分析
这章最值得追的不是 HTTP 层，而是“服务状态如何进入 runtime”：

- `vllm/v1/engine/core.py`：主循环如何把服务请求转成 scheduler/worker 协议。
- `vllm/v1/executor/abstract.py`：不同部署形态为何能复用同一套 runtime。
- `vllm/distributed/kv_transfer/kv_connector/base.py`：远端 KV 为什么不是外挂，而是正式 connector 契约。
- `vllm/distributed/ec_transfer/ec_transfer_state.py`：encoder cache 迁移也被纳入正式状态机。

### vLLM-Ascend 补充
Ascend 的服务增量不是“也能 serve”，而是把面向大规模实例的服务机制进一步平台化。`vllm_ascend/core/recompute_scheduler.py` 为 PD/disaggregated 场景重写了 scheduler 与 remote KV 状态机，把远端 KV、placeholder token 与异步 connector 状态揉进同一条服务路径；`vllm_ascend/core/scheduler_dynamic_batch.py` 基于 SLO/profile table 动态收缩或放宽 batch，并把 profiling 结果回灌到预算细化；`vllm_ascend/distributed/kv_transfer/ascend_multi_connector.py` 把 layerwise KV connector 纳入多 connector 协调；`vllm_ascend/model_loader/netloader/netloader.py` 与 `rfork_loader.py` 继续把远程装载与弹性部署做进 serving 路径。这一章的关键词不是“功能兼容”，而是“围绕 NPU 集群服务把上游拓扑进一步工程化”。

## 第 9 部分. 如何分析 TPU 代码

### 核心问题
性能分析章节的本质，是把“为什么快/为什么慢”从感觉变成可观测对象。对推理系统而言，单个 kernel profile 不够，还必须看 scheduler、KV usage、graph capture 命中率、token throughput、queueing 行为。

### vLLM 的技术体现
upstream vLLM 已经把相当多的可观测点做进系统内部：`SchedulerStats`、`KVCacheMetricsCollector`、`PrefixCacheStats`、`SpecDecodingStats`、`CUDAGraphLogging`、`compilation_counter` 等都在不同层跟踪运行时状态。也就是说，vLLM 不只是在代码外写 benchmark 脚本，而是把 profiling 与 observability 直接嵌入了调度器、KV 系统和 graph runtime。

### 工程技术方案
这一章最有价值的技术体现有三类：

1. 调度和 cache 内部统计：命中率、usage、prefix 复用、spec decode 指标；
2. 编译/图执行统计：capture/replay 情况、padding、runtime mode；
3. 引擎级指标：iteration stats、吞吐、未完成请求数、输出流式延迟。

### 源码分析
这一章的代码要按“能定位什么问题”来读：

- `vllm/v1/core/kv_cache_metrics.py`：定位 cache pressure 和 prefix reuse 问题。
- `vllm/v1/metrics/stats.py`：定位 scheduler 是否真的把 token budget 打满。
- `vllm/v1/spec_decode/metrics.py`：定位 speculative path 是在加速还是在制造回退。
- `vllm/compilation/cuda_graph.py` 与 `compilation/counter.py`：定位 graph capture 是否真正命中。

如果只看 profiler trace，不看这些系统级指标，很多 serving 瓶颈会被误判成“某个 kernel 不够快”。

### vLLM-Ascend 补充
Ascend 在 profiling 章节有非常真实的系统增量。`vllm_ascend/profiling_config.py` 会生成 `service_profiling_symbols.yaml`；`vllm_ascend/core/profiling_chunk_predictor.py` 与 `scheduler_profiling_chunk.py` 把启动阶段的真实 prefill 测量反馈成 chunk size 预测；`vllm_ascend/worker/v2/aclgraph_utils.py` 则让 full-graph replay 过程中 attention 参数还能保持可更新、可调优。再加上 `vllm_ascend/cpu_binding.py` 对 A2/A3/310P 做的拓扑感知绑核，可以看出 Ascend 把性能分析从“单个 profiler”扩展成了“调度、图、主机侧一起调”的服务级工作流。

## 第 10 部分. 在 JAX 中编程 TPU

### 核心问题
这一章原本强调的是“如何在框架 IR、编译器和图层面与硬件对齐”。对 vLLM 来说，最贴切的对应不是 JAX/XLA，而是 `torch.compile + inductor passes + CUDA graph / static graph` 这条 PyTorch 时代的编译路径。

### vLLM 的技术体现
vLLM 的 `compilation/` 目录本身就是一个“编译期工程层”：它有 backend、wrapper、base static graph、pass manager、fusion/utility/IR passes，以及与 CUDAGraph 互锁的 runtime wrapper。书里谈 JAX，是在说“不要把硬件友好性只看成 kernel 级问题”；vLLM 这里的回答则是“推理系统也需要自己的图和编译中间层”。

### 工程技术方案
这里最重要的不是某个 pass，而是整体结构：

1. `compiler_interface.py` 和 `backends.py` 负责编译入口；
2. `pass_manager.py` 与 `vllm_inductor_pass.py` 负责图重写与融合；
3. `base_static_graph.py` 与 `cuda_graph.py` 负责静态图与 runtime capture/replay；
4. 这些组件最终服务的不是训练图，而是在线推理里极度敏感的 decode 小步执行。

### 源码分析
这一章在 upstream 最值得对照的是“图如何进入 runtime”：

- `vllm/compilation/compiler_interface.py`：编译入口。
- `vllm/compilation/passes/pass_manager.py`：pass 如何被组织。
- `vllm/compilation/passes/vllm_inductor_pass.py`：推理图到底被改了什么。
- `vllm/compilation/base_static_graph.py` 与 `cuda_graph.py`：静态图如何和 runtime replay 接上。

所以本章对应的不是“JAX API 替身”，而是“图编译如何成为推理系统正式组成部分”。

### vLLM-Ascend 补充
如果把书里这一章的 JAX/XLA 编程观念翻译到 Ascend 世界，对位物就是 `torch-npu + ACLGraph + graph fusion pass + torchair patch`。`vllm_ascend/compilation/acl_graph.py` 负责 capture/replay；`compiler_interface.py` 在 fusion pass 与 `torchair` backend 之间切换；`graph_fusion_pass_manager.py` 与 `norm_quant_fusion_pass.py`、`sequence_parallelism.py`、`allgather_chunk_noop_pass.py` 说明 Ascend 不是照单全收上游的 Triton/Inductor 组织方式，而是明确在图重写层做 NPU 取向的 pass。`meta_registration.py` 与 `patch/worker/patch_npugraph_ex_triton.py` 进一步说明它甚至要为 tracing/export/graph conversion 补 Meta 实现与 monkey patch。

## 第 11 部分. 结论和进一步阅读

### 核心问题
书的结论章节通常做两件事：把前面的抽象重新收束成几个关键原则，并指出哪些原则在具体系统里最值钱。对 vLLM 来说，真正值得记住的并不是 feature 列表，而是“哪些系统不变量让它能不断叠加新能力还不散架”。

### vLLM 的技术体现
从源码结构看，vLLM 至少有三个稳定不变量：

1. 调度层围绕 `num_computed_tokens` 与 `num_tokens_with_spec` 建模请求推进；
2. KV 系统围绕 block/page 抽象组织缓存，而不是让模型层直接持有大块连续状态；
3. 执行层围绕 backend / worker / compilation wrapper 做平台与内核差异分派。

### 工程技术方案
如果要把整套系统压缩成一句话，可以写成：

**vLLM 用 block 化 KV 管理支撑连续调度，再用 backend/graph/executor/connector 把这个调度模型扩展到多硬件、多拓扑、多工作负载。**

### 源码分析
结论章节最适合回读四个核心文件：

- `vllm/v1/core/sched/scheduler.py`
- `vllm/v1/core/kv_cache_manager.py`
- `vllm/v1/worker/gpu/model_runner.py`
- `vllm/compilation/cuda_graph.py`

如果这四条线已经能在脑中串起来，再去看 MoE、spec decode、connector、distributed，理解成本会低很多。

### vLLM-Ascend 补充
Ascend 最值得观察的点恰恰是“哪些东西没变”。它没有改写 vLLM 的三大不变量：请求推进仍以 token debt 为中心，KV 仍以 block/page 为中心，执行仍然通过 backend/worker/graph wrapper 组合出来。真正变化的是平台、算子、图执行、调度细节和 host 绑定层；也正因为这些系统边界保持稳定，Ascend 的平台特化才能持续跟进上游而不必重写整个 serving 模型。

## 第 12 部分. 如何看待 GPU

### 核心问题
GPU 章节的本质是理解“为什么某些实现方式更适合 GPU”。对 vLLM 来说，这直接关系到 attention backend 选择、paged attention 的 block 布局、graph capture 的收益、通信库与显存分配策略。

### vLLM 的技术体现
upstream vLLM 仍然是以 GPU 为主战场设计的：`platforms/cuda.py`、`worker/gpu/`、`attention/backends/flash_attn.py`、`attention/ops/triton_*`、`device_communicators/pynccl*.py` 等路径共同定义了 GPU execution path。也就是说，GPU 不是“运行环境背景板”，而是 vLLM 的许多核心抽象最早被验证、打磨和稳定化的地方。

### 工程技术方案
GPU 章节在 vLLM 上主要体现为：

1. 用 attention backend 体系屏蔽不同 kernel 实现；
2. 用 paged KV/block table 适配显存利用率与 decode 访存形态；
3. 用 CUDA graph 与 persistent workspace 减少高频 launch 成本；
4. 用 NCCL/pynccl 与 parallel_state 处理多 GPU 通信。

### 源码分析
这一章最值得看的不是“有多少个 GPU kernel”，而是“GPU 假设被埋在哪些层”：

- `vllm/platforms/cuda.py`：平台能力、dtype、backend 优先级。
- `vllm/v1/worker/gpu/model_runner.py`：GPU 快路径的真实控制面。
- `vllm/distributed/device_communicators/pynccl.py`：通信库也是平台契约的一部分。
- `vllm/device_allocator/cumem.py`：显存分配策略同样是 runtime 设计的一环。

### vLLM-Ascend 补充
这一章也高度集中地体现了 Ascend 差异。Ascend 插件里大量补丁都在做“去 CUDA 假设”：`vllm_ascend/patch/platform/patch_torch_accelerator.py` 把 `torch.accelerator.*` 重定向到 `torch.npu.*`；`patch/worker/patch_cudagraph.py` 修正上游 CUDAGraph dispatcher 的 padding/shape 假设；`patch/worker/patch_triton.py` 把部分 Triton/Mamba/FLA 内核入口换成 Ascend 实现；`patch/worker/patch_npugraph_ex_triton.py` 甚至连 `torchair`/FX graph converter 都要 patch。它们覆盖的不是 cosmetic rename，而是 accelerator API、graph dispatcher、kernel registry 与 FX conversion 这些深绑 GPU 假设的层级；这也说明很多看似通用的高性能推理技巧，一旦迁移到 NPU，最终都必须重新显式化。
